# Zenith audit and continuation handoff — 10 September 2026

## 1. Executive verdict

Zenith launches as an Electron desktop app in development and from the production `dist/index.html`. The actual filesystem, Monaco and PTY integrations exist. The observed editor/save/terminal/theme regressions are being covered by repeatable fixture-based tests, not inferred from compilation.

The core UTF-8 editing workflow passes runtime checks, including editing during a save, disk-byte verification, rejected dirty-tab closure, and model/selection/undo preservation. All 14 development desktop assertions pass, but that harness still exited 1 after reporting zero assertion failures, alongside ConPTY teardown errors: it is not a clean end-to-end process pass. Native folder chooser interaction is **not** verified: the harness substitutes its returned directory while exercising the actual Open Folder button, preload, main process and filesystem. Ctrl+S is exercised with a renderer keyboard event; native injected keystrokes were unreliable in this environment. No screenshot visual certification is claimed (`capturePage` returned `UnknownVizError`).

This is a working editor foundation, not a production-ready IDE. The highest current product data-safety gap is absent crash/hot-exit recovery. The disconnected AI prototype has additional high-risk write/cancellation/privacy gaps and must not be exposed as a completed Nova integration. Finish foundation acceptance, then implement recovery and essential file operations before expanding AI.

## 8. Theme repair report

There is one active theme authority: `ThemeProvider.preferences.selectedThemeId`. `appearanceMode` is registry metadata. The two preferred IDs are global and shown once under ThemeBrowser's advanced controls, not per-card switches. CSS tokens, Monaco and xterm derive from that selected registry object.

`zenith-theme-preferences-v1` takes precedence. If absent, the three legacy keys (`zenith-theme`, `zenith-light-theme`, `zenith-dark-theme`) migrate once, then are removed. Corrupt JSON/IDs fall back to registry `light`, preferred `light`, preferred `dark`. Mixed-theme toggle uses declared preference or Monaco tone. The harness clicks every card and checks unchanged editor/model/xterm identities plus undo availability, then exercises quick toggle. Production renderer reload retains selected ID. Cursor/selection across tabs is checked separately; scroll position, custom preferred pairs and full process-relaunch persistence still need explicit proof.

## 11. Recommended next phases

Common definition of done for every phase: observable acceptance in actual Electron, regression tests, typecheck/lint/build, no golden-flow regression, documented errors/privacy implications, reviewed diff. Complexity estimates reflect architecture and verification, not calendar promises. Rollback means a scoped reviewable patch and safe data migration; never reset unrelated changes.

### F0 — Finish foundation acceptance (immediate next gate)

**Goal/value:** certify daily editing and eliminate known release blockers. **Scope:** remaining resize/focus lifecycle, PTY teardown/reload process accounting, native picker/close dialogs, persisted-setting corruption, external-write recovery UX, honest unsupported settings. **Excludes:** AI integration, redesign, dependency upgrades. **Impact/modules:** App, terminal/resize, main lifecycle, editor/workspace stores, Settings, audit scripts. **Prerequisite:** preserve current repair batch. **Security:** test only fixtures; no real repo mutation. **Order:** finish failed assertions → add reload/close lifecycle tests → perform native picker/keyboard/scale checks → classify residuals. **Acceptance/tests:** 960×680 and larger usable; repeated drags/cancel; no lost dirty files; no orphan PTYs after reload/exit; golden flow passes. **Done:** all current P0/P1 closed or a precise release blocker recorded. **Risk/rollback:** event-order regressions; keep each lifecycle change isolated. **Complexity:** Medium because native focus/process testing is environment-dependent.

### F1 — Recovery and essential workspace operations

**Goal/value:** protect work through crashes and make normal file management possible. **Scope:** versioned recovery journal, recent workspaces, recover/discard UI, atomic create/rename/trash, tab reconciliation, quick-open/palette acceptance. **Excludes:** sync, permanent delete by default, multi-root/splits. **Impact/modules:** WorkspaceService, preload/types, workspace/editor stores, Explorer, palette, settings. **Prerequisite:** F0. **Security:** realpath and workspace-generation checks, restrictive recovery storage, retention controls. **Order:** recovery format → crash fixture → startup recovery UI → safe file operations → palette consistency. **Acceptance/tests:** crash/restart recovers exact dirty bytes; stale disk conflicts cannot overwrite silently; rename keeps active buffer; trash requires explicit intent; path traversal tests. **Done:** complete recovery and file-management vertical flows. **Risk/rollback:** stale journals and name collisions; retain original recovery copy until confirmed. **Complexity:** Medium, focused on persistence and transactions.

### F2 — Source control completion

**Goal/value:** inspect and commit understandable changes. **Scope:** read-only Monaco diff, staged/unstaged views, branches/history/conflicts, reliable refresh, clear upstream/auth errors. **Excludes:** automatic commit/push, destructive reset/rebase UI. **Impact/modules:** GitService, typed bridge, gitStore/GitPanel, diff tabs. **Prerequisites:** F0/F1 editor ownership. **Security:** literal paths, trusted repo hooks, narrow credential transport, explicit remote intent. **Order:** diff API → model lifecycle → status/branches/conflicts → authenticated transport. **Acceptance/tests:** disposable repos with rename/conflict/empty HEAD/nested roots; end-to-end stage/unstage/commit; only local bare remotes in automation. **Done:** full inspect-to-local-commit workflow plus explicit remote states. **Risk/rollback:** index/worktree confusion; keep read-only diff first and feature changes separable. **Complexity:** Medium.

### F3 — Nova provider and inspectable read-only assistance

**Goal/value:** real project-aware assistance with visible data boundaries. **Scope:** retain Nova name, secure provider settings and typed preload API, streaming/cancel/retry/errors, explicit file/selection context and secret exclusions, usage display, read-only explain actions. **Excludes:** applying edits, running scripts, orchestration, semantic indexing. **Impact/modules:** AI provider/config/context/conversations, AIPanel/new AI store, Settings, preload/types. **Prerequisites:** F0–F2, explicit privacy/context design. **Security:** no implicit Git diff upload; consent before provider requests; key stays in main; fail closed on incomplete streams. **Order:** offline fake-provider contract tests → streaming/cancel parser → context preview → settings → real read-only chat with explicitly supplied test credentials. **Acceptance/tests:** offline/401/429/incomplete/abort paths; no extra request after cancel; exact displayed context equals transmitted context. **Done:** verified real assistant workflow with observable usage/errors. **Risk/rollback:** accidental code disclosure; keep network integration disabled until acceptance. **Complexity:** Medium.

### F4 — Nova safe single-agent edits

**Goal/value:** reviewable, reversible code changes. **Scope:** proposed diff, exact approval-bound content, dirty/external conflict checks, checkpoints, atomic apply/recovery, explicit command contents/approval, pinned workspace, cancellation and audit trail. **Excludes:** concurrent agents and automatic Git/dependency actions. **Impact/modules:** edit-service, validation-service, orchestrator replacement/refactoring as needed, editor reconciliation/diff UI. **Prerequisites:** F1 recovery and F3. **Security:** disallow secret paths, bind approval to proposal and script hashes, treat package scripts as arbitrary code, recheck real parents at mutation. **Order:** transactional/checkpoint tests → cancel/workspace switches → diff approval → editor sync → optional command runner. **Acceptance/tests:** reject/abort writes nothing; cancellation at every boundary; stale approvals fail; partial apply recovers exact bytes; no undisclosed command. **Done:** one bounded agent completes a disposable edit/review/test/undo workflow. **Risk/rollback:** highest data-safety risk; preserve checkpoints and retain disabled rollout gate. **Complexity:** Large.

### F5 — Language and developer tooling (separate increments)
